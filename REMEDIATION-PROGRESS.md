- E1: added infrastructure fault injection, closing `G7-T5`. `tests/integration/chaos.integration.test.ts` covers executor death after submit, PostgreSQL restart, Redis restart, and worker reconnection (8 cases), each ending in the same invariant: one execution row, and zero on every confirmed quantity. Faults are injected where the outage is observable to the process rather than by stopping containers — CI runs against service containers it cannot restart, so a container-stopping suite would only ever pass on a developer's docker-compose. A PostgreSQL restart is therefore `pg_terminate_backend` on every backend but the issuing one; a Redis restart is `CLIENT KILL TYPE normal` plus dropping the queue's own keys (fixture-scoped, never `FLUSHALL`, since `REDIS_URL` may be a shared local instance). The Redis case is deliberately inverted from the others: Redis is not the safety mechanism, so losing it must lose at most the job, never the ledger. **The suite found a real production defect**: a terminated backend emits `'error'` on the *checked-out* client, which `attachPoolErrorHandler` does not cover (it handles idle clients only), so a database restart during any canonical-lifecycle transaction would have crashed the whole service instead of failing one transaction. The new `packages/db/src/transaction.ts` `withTransaction` listens for the duration, preserves the original error when the rollback on the dead backend also fails, and calls `release(true)` so the dead socket is destroyed rather than handed to the next caller; `copy-trade-lifecycle.ts` and `copy-eligibility.ts` both delegate to it. Tests: `packages/db/src/transaction.test.ts` (7), `tests/integration/chaos.integration.test.ts` (8).

- Found via those docs while verifying E2's Polymarket ingestion stage, and fixed: `backfillPolymarketWallet` walked `offset` forward without bound. The Data API **rejects** an offset past 10000 with a 400 instead of clamping it, and the loop accumulated pages in memory and only persisted after it finished — so any wallet with more than 10000 fills threw and lost the entire backfill, including the ~10000 trades already read. High-volume wallets are precisely the ones SWAT tracks, so this was a silent total failure on the most valuable targets. Paging is now windowed (`fetchConfirmedPolymarketTradePages`, exported for test): when a window's offset budget is spent it re-anchors `end` on the oldest fill seen and opens a fresh window, as the docs prescribe. Boundary repeats are harmless — `recordConfirmedPolymarketTrade` dedupes on its natural key and the source-trade fill index hashes the same identity. A window that cannot advance stops and **warns** rather than truncating silently. Page size went 100 → 500 (the API clamps `limit` at 10000; `/trades` allows 200 req/10s), cutting request count ~5x. Four cases in `apps/indexer/src/polymarket.test.ts` cover the offset walk, the re-anchor, the non-advancing stop, and error propagation.
- **Not changed, flagged for a decision:** `/trades` defaults `takerOnly=true`, so maker-side fills are invisible to ingestion today. For copy-trading a wallet that provides liquidity that is a real coverage gap, but flipping it changes what the pipeline considers a source trade, so it wants an explicit call rather than a silent default change.
