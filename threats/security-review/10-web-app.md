### WEB-01 / WEB-02 — Testbed custody and withdrawal intent

The testbed's actual signing vault is a keypair, whereas the UI also derives/displays a canonical PDA and states creator-only protection (`pda-test-ui/server.mjs:38-41,102-107,243-284`; `pda-test-ui/public/index.html:348-374,654-670`). The client prefers `currentInteractiveVault` for deposits, making the unsafe keypair a concrete funding destination, not unused demo code (`pda-test-ui/public/index.html:709-738`). Default server RPC is devnet, but `SOLANA_RPC_URL` can override it while status responses still say devnet; no cluster validation appears in the reviewed startup (`pda-test-ui/server.mjs:17-22,67-85`). Severity is High, not Critical, because real funding and non-test deployment are **NOT VERIFIED**.

The browser constructs a message containing amount/owner/timestamp, but the server never reconstructs and compares that intent; it verifies whatever `message` arrives (`pda-test-ui/public/index.html:826-861`; `pda-test-ui/server.mjs:206-230`). Timestamp freshness uses `parseInt` and a greater-than comparison without a finite-integer check; replay state is absent from the full route (`pda-test-ui/server.mjs:214-285`). The server's transfer destination is specifically `ownerPk` (`pda-test-ui/server.mjs:272-277`). The simulated unauthorized test always returns `blocked: true`, including caught failures, so its green UI banner is not evidence that this signing vault is theft-resistant (`pda-test-ui/server.mjs:174-197`; `pda-test-ui/public/index.html:789-802`).

**Abuse concept 1:** public-input signing authority or a captured owner signature compromises funded interactive-vault intent. No keys were derived, signatures generated or transactions submitted.

1. Disable interactive deposits/server withdrawals until the public-input keypair is removed. Isolate testbed listeners to loopback by default and fail closed on unsupported clusters (`pda-test-ui/server.mjs:17-22,374-389`). Inventory any historically funded derived accounts through a separately authorized remediation process; do not simply change derivation and strand funds.
2. Use real program-controlled PDA operations or a clearly labeled inert/mock demonstration. Update vault-info, `derivePda`, deposit selection and withdrawal UI together so no caller silently falls back to an unsafe alternative (`pda-test-ui/server.mjs:89-130`; `pda-test-ui/public/index.html:663-678,709-738,813-863`).
3. If retaining signed intents, canonically bind action, owner, vault, destination, integer amount, cluster, timestamp and server-issued nonce. Compare the exact signed intent, enforce finite safe ranges and atomically consume nonce before a signing side effect; coordinate this protocol change with the browser message builder (`pda-test-ui/server.mjs:202-285`; `pda-test-ui/public/index.html:826-863`).

### WEB-03 — HTML sinks and errors

Some PDA HTML writes are fixed status strings, but log/error/result writes incorporate runtime text; treating every `innerHTML` call as equally exploitable would be inaccurate (`pda-test-ui/public/index.html:517-529,789-805,876-883`). The in-browser keypair remains in script-accessible memory, increasing possible consequences of a successful same-origin script injection (`pda-test-ui/public/index.html:620-645`). By contrast, reviewed Next signal/log/error rendering uses React text, not HTML interpolation (`apps/web/app/signals/page.tsx:58-74`; `apps/web/app/logs/page.tsx:448-451`; `apps/web/app/login/page.tsx:117-120`).

**Abuse concept 2:** malicious upstream/provider text becomes markup in the signing test UI; victim-path control remains a test prerequisite, not a demonstrated exploit.

1. Build formatting with DOM nodes and set variable values with `textContent`; validate explorer link origin/protocol before assigning `href` (`pda-test-ui/public/index.html:747-749,795-805,876-883`).
2. Return stable public error codes and keep raw details in protected diagnostics; preserve the UI's success/error response contract (`pda-test-ui/server.mjs:132-135,189-197,299-302`).

### WEB-04 / WEB-05 / WEB-06 — Transport, navigation and headers

**Abuse concept 3:** an untrusted upstream/transport receives cookies, or a crafted post-login destination is normalized unexpectedly. These are conditional transport/navigation risks; no interception or off-origin navigation was tested (`apps/web/middleware.ts:38-46`; `apps/web/app/login/page.tsx:45-57`).

1. Share one validated backend resolver across rewrites, middleware and SSR; require HTTPS for external hosts and explicitly allow reviewed loopback/private development cases. Reject URL userinfo and unexpected protocols. Current `sanitizeUrl` checks only `startsWith('http')`, and resolver precedence differs between config and middleware (`apps/web/next.config.ts:4-16`; `apps/web/middleware.ts:21-25`; `apps/web/lib/api.ts:124-136`).
2. Forward only `swat_session` in middleware, as SSR already does; set an explicit redirect policy and validate upstream redirects before forwarding credentials (`apps/web/middleware.ts:38-46`; `apps/web/lib/api-server.ts:39-47`). Actual Fetch redirect behavior is **NOT VERIFIED**.
3. Normalize `next` into a same-origin URL, reject ambiguous syntax, use the parsed pathname for shared admin classification and keep safe defaults. Eliminate duplicated admin-prefix logic without weakening backend role checks (`apps/web/app/login/page.tsx:40-57`; `apps/web/lib/route-access.ts:38-58`).
4. Add anti-framing and MIME/referrer protections plus CSP compatible with the existing fixed inline bootstrap and font stylesheet; do not enable broad unsafe script allowances merely to preserve it (`apps/web/app/layout.tsx:69-89`). Roll out HSTS only for verified HTTPS deployments.

## C. Invariants and safe local tests

**All tests NOT RUN.** Use mocked requests, inert text, synthetic accounts and fake RPC/signing ports; never send transactions.

- Invalid/reused or amount/cluster-altered authorization must reach zero signer calls; a PDA must never be substituted with a public-input signing account (WEB-01/02 paths above).
- RPC/provider error text must remain literal text; explorer URLs must remain allowed HTTPS destinations (WEB-03 paths above).
- Middleware forwards only the intended cookie to a validated backend, refuses unknown roles and never caches identity; SSR remains uncached (`apps/web/middleware.ts:37-53`; `apps/web/lib/api-server.ts:39-52`).
- A shared pure redirect validator rejects ambiguous destinations; app rendering with a forged cookie never substitutes for API authorization (`apps/web/lib/route-access.ts:89-114`; `apps/api/src/auth/plugin.ts:135-162`). Existing route/API tests cover pure classification, credentials and CSRF building, not real middleware, login normalization or PDA signing (`apps/web/lib/route-access.test.ts:4-87`; `apps/web/lib/api.test.ts:40-109,123-181`).
