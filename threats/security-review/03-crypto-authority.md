## A. Boundaries and authority map

The intended boundary is protocol-enforced, scoped, revocable, expiring delegation, not merely application checks (/home/xahmie/Documents/SWAT/docs/adr/0003-delegated-execution-authority.md:11–18). The README claims self-custodial execution and cryptographic non-custody (/home/xahmie/Documents/SWAT/README.md:3–5,32,151); those are documentation claims, not deployment evidence. ADR2 is superseded for user root keys, while explicitly retaining operator/SOPS secret concerns (/home/xahmie/Documents/SWAT/docs/adr/0002-custody-key-store.md:3–19).

**Secret map.** `sealSecret` creates a fresh 32-byte data-encryption key and 12-byte GCM nonce; the wrapped key has its own random 12-byte nonce (/home/xahmie/Documents/SWAT/packages/shared/src/authority/envelope.ts:38–49; /home/xahmie/Documents/SWAT/packages/shared/src/authority/key-wrapper.ts:71–84). `CUSTODY_MASTER_KEY` / `CUSTODY_MASTER_KEY_HEX` are environment-based wrapping-key inputs; `env:v<n>` is a wrapper label, not automatic key rotation (/home/xahmie/Documents/SWAT/packages/shared/src/authority/key-wrapper.ts:42–68). The API currently seals JSON containing `apiKey`, `secret`, `passphrase`, and `signerAddress`, **not a wallet private key** (/home/xahmie/Documents/SWAT/apps/api/src/routes/me.ts:611–623). `SOLANA_PRIVATE_KEY` feeds the operator transaction signer (/home/xahmie/Documents/SWAT/apps/trade-executor/src/solana-signer.ts:112–120). EVM and Polymarket actual signing accessors use `evmAccount.signTypedData` and `polymarketSigner._signTypedData` (/home/xahmie/Documents/SWAT/apps/trade-executor/src/index.ts:1132–1158); their key-loading modules were not deeply reviewed. SOPS/escrow distribution is a documented operational concern, **NOT VERIFIED** in host configuration (/home/xahmie/Documents/SWAT/docs/adr/0002-custody-key-store.md:103–106,165–171).

**Identity boundary.** Encryption AAD is exactly `(userId, chainKind, keyVersion)`, not concrete chain, account, purpose, or grant identity (/home/xahmie/Documents/SWAT/packages/shared/src/authority/key-wrapper.ts:7–11,27–29). The database instead distinguishes concrete chain and account and permits several grant kinds (/home/xahmie/Documents/SWAT/packages/db/sql/047_user_execution_grants.sql:31–71,113–127). A decrypting consumer must reconstruct authenticated identity from trusted row context; none was found in the searched application caller paths for `openSealedSecret` (/home/xahmie/Documents/SWAT/packages/shared/src/authority/envelope.ts:70–74; /home/xahmie/Documents/SWAT/packages/db/src/execution-grants.ts:315–327; repository symbol crosscheck recorded below).

**Policy/signing boundary.** The policy engine can decode a single account `execute` and its inner call, reject unknown selectors, constrain arguments, and default-deny (/home/xahmie/Documents/SWAT/packages/shared/src/authority/evm-calldata.ts:169–190,304–359; /home/xahmie/Documents/SWAT/packages/shared/src/authority/permission-policy.ts:1122–1194). Only `permit` is authorization success (/home/xahmie/Documents/SWAT/packages/shared/src/authority/permission-policy.ts:349–354). But actual signer integration is separate: the Solana adapter forwards transaction bytes, whereas production Jupiter runtime is independently bound to an environment signer (/home/xahmie/Documents/SWAT/apps/trade-executor/src/execution-authority-adapters.ts:136–176; /home/xahmie/Documents/SWAT/apps/trade-executor/src/jupiter-jito-config.ts:91–117). Per-user Robinhood and Polymarket adapters still deny, a real mitigation against treating database metadata as working delegation (/home/xahmie/Documents/SWAT/apps/trade-executor/src/execution-authority-adapters.ts:462–467,585–593).

**Authentication/withdrawal boundary.** Wallet login/link challenges bind address, kind, origin-derived domain/URI, and a random nonce with a 300-second Redis TTL; verification atomically consumes it with `GETDEL` (/home/xahmie/Documents/SWAT/apps/api/src/auth/routes.ts:222–273,276–325; /home/xahmie/Documents/SWAT/apps/api/src/auth/wallet-signature.ts:34–38,116–143). The separate withdrawal signature helper verifies owner Ed25519 signatures, but only enforces age/future bounds, not one-time nonce consumption (/home/xahmie/Documents/SWAT/packages/shared/src/authority/withdrawal-authorization.ts:55–149). Actual API withdrawal uses linked-wallet verification, cooling-off, email OTP, and deletion; it returns a confirmation object, with no enqueue/transaction call in the inspected handler (/home/xahmie/Documents/SWAT/apps/api/src/routes/me.ts:1131–1297). Do not conflate these three mechanisms.
