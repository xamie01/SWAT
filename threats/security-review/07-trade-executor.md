## A. Boundaries and execution map

The worker accepts Redis/BullMQ data rather than authenticated HTTP. It validates signal ID, token string, score, and supported chain, but casts the rest of the payload; a missing, blank, or nonstring `userId` selects operator authority (`apps/trade-executor/src/index.ts:1408-1459,1097-1100`). Queue publish access is therefore a money-path privilege; public access to Redis is **NOT VERIFIED**. Fan-out really does enqueue user jobs, despite obsolete executor comments saying otherwise (`apps/signal-engine/src/index.ts:522-552`; `apps/signal-engine/src/fanout-enqueue.ts:242-255`). The local registry prevents mismatched principal kinds, user IDs, and chains, but does not establish that signing bytes or settlement funds belong to that principal (`apps/trade-executor/src/execution-authority.ts:328-374`).

Exact queues are `swat-trades-solana`, `swat-trades-polygon`, `swat-trades-robinhood`, `swat-trades-base`, `swat-trades-ethereum`, and `swat-trades-bsc`; legacy `swat-trades` remains a default-on drain worker (`packages/shared/src/constants.ts:32,48-54`; `apps/trade-executor/src/trade-workers.ts:76-103`). Production creates one Worker for each specification and executes misrouted jobs after logging (`apps/trade-executor/src/index.ts:2893-2902`; `apps/trade-executor/src/trade-workers.ts:120-130`). Default concurrency is one per specification; Solana and Polygon can independently be configured up to ten (`apps/trade-executor/src/trade-workers.ts:39-65`). Thus the current implementation creates six chain workers plus a legacy worker, not the three total claimed in nearby comments. Live Base/Ethereum/BSC dispatch is rejected as missing implementation (`apps/trade-executor/src/index.ts:2409-2410`).

Signal-engine producer job name is `signal-trade`, with four attempts, exponential backoff starting at 5,000 ms, and remove-on-complete; operator jobs are added before users, sequentially (`apps/signal-engine/src/fanout-enqueue.ts:58,119-120,225-255,349-359`). Executor dispatch is Worker → account/chain breaker → `handleJob` → current platform mode/startup clamp → sizing/exposure → authority → claim → venue. The default authority construction is explicit in production (`apps/trade-executor/src/index.ts:960-1035,1462-1618,2891-2902`).

Solana live selection is configured Jupiter/Jito or operator-only Trojan (`apps/trade-executor/src/index.ts:1768-1795,1895-1909`). Jupiter dispatch obtains a quote, the runtime builds bytes, optionally simulates, fetches tip metadata, signs through a process-bound signer, and submits a bundle (`apps/trade-executor/src/solana-dispatch.ts:171-186`; `apps/trade-executor/src/jupiter-jito-runtime.ts:238-342`). RHC uses a process-local account lock plus PostgreSQL nonce lock, bounded exact approval and swap simulations, then receipt observation (`apps/trade-executor/src/robinhood.ts:680-711,795-899`; `packages/db/src/evm-nonce.ts:81-127`). Polymarket checks active local executions/open orders, balance, book depth, mirror bound, market state and source freshness, creates a signed FAK order, posts it, and waits for attributable confirmed fills (`apps/trade-executor/src/polymarket.ts:684-985`). User RHC and Polymarket adapters deny; they do not fall back to an operator grant (`apps/trade-executor/src/execution-authority-adapters.ts:462-467,585-593`).

Timers are intervals, not cron: main starts `reconcilePending` once, then every 60,000 ms; independent `pollPolymarketOrders` runs every 60,000 ms (`apps/trade-executor/src/index.ts:2879-2881,2916-2924`). Reconciliation coordinates venue sweeps, redemption, canonical backstop, then an exit escalation sweep (`apps/trade-executor/src/index.ts:2722-2863`). This review did not verify redemption or ladder internals.

### Numbered remediation and compatibility notes

1. **EXE-01: separate operator execution from delegated execution.** The factory must not use `deps.solana.signer` as user authority. Require a valid canonical settlement address, installed adapter, active grant, expiry/revocation checks, and a transaction that invokes the scoped program with bounded accounts and amounts. Preserve the existing operator adapter and operator Trojan path. Keep user RHC/PM denial codes stable. Merely calling `authority.sign` is insufficient if that method still signs arbitrary bytes using operator keys (`apps/trade-executor/src/execution-authority-adapters.ts:136-175,608-614`). Grant-table issuance, deployed program implementation and audit assertions were **NOT VERIFIED**.

2. **EXE-02: make tenant identity mandatory for user paths.** Extend `prepareCanonicalExecutions` and `persistTrade` with explicit normalized `userId`; pass it to DB methods, cross-check returned execution principal and venue settlement, and reject mismatches before effects. Retain explicit null only for legacy operator callers. Database queries already support tenant-scoped keys and evidence (`packages/db/src/copy-trade-lifecycle.ts:1834-1842,1980-2015`; `packages/db/src/trades.ts:17,179`), so fix callers rather than removing SQL tenancy. Existing null financial history cannot safely be relabeled without evidence.

3. **EXE-03: enforce current tenant choice, not informational mirrors.** At dequeue, load the user's mode/tolerance and compare with the enqueued policy revision; clamp by platform capabilities, never widen paper/off to live. Either regenerate projections under the narrower mode or reject outdated jobs. Add a Polymarket tolerance parameter shared by book-walk, master-price bound and paper simulation; preserve explicitly tighter limits. Solana live default is 1,500 bps while paper Jupiter uses literal 150; PM uses environment default 200 rather than the shared Polygon default 300 (`packages/shared/src/slippage.ts:29-35`; `apps/trade-executor/src/index.ts:2470-2475`; `apps/trade-executor/src/polymarket.ts:741`). These are policy discrepancies, not measured execution slippage.

4. **EXE-04: reserve risk before the money path.** Parse the daily ceiling with the existing finite-number helpers, reject invalid pricing, and distinguish native ETH from RHC ERC20 base spend. Acquire an account/chain/mode reservation atomically before dispatch, include all unknown/pending and partial residual commitments, release only on proven cancellation/failure, and accrue actual fills idempotently. Shadow stays separate; decide explicitly whether paper has its own budget. A concurrency-one worker is not a cross-process reservation. Adjacent capacity accrual also logs and continues on ledger failure (`apps/trade-executor/src/index.ts:1319-1338`); do not mistake that lower-bound numerator for guaranteed capacity enforcement.

5. **EXE-05: bind bytes to intent.** Validate requested quote identities/amounts, inspect resolved lookup-table accounts against trusted observations, constrain programs, token accounts, owner/recipient, maximum debit, minimum credit, approvals, close-account destinations, tips and compute fees. Reject extra instructions and unknown layouts. Check the final serialized message hash immediately before signing; simulation is an additional execution check, not authorization. Preserve valid setup/wrap/cleanup paths through narrowly tested allowlists rather than blindly prohibiting all auxiliary instructions (`packages/shared/src/jupiter-swap.ts:232-247`).

6. **EXE-06/09: use durable submitting/unknown states.** Persist stable intent, signed bytes/order hash, transaction signature if locally derivable, expiry window and ownership before external POST. Use a database/Redis CAS lease keyed to tenant/client order ID. On transport or persistence uncertainty retain reservations and an unknown state; do not release the signal or terminate canonical execution. Recovery should resend identical signed artifacts only where venue idempotency is established, otherwise probe and escalate. RHC already writes `submission_unknown` before `send` (`apps/trade-executor/src/robinhood.ts:637-658`); preserve that safer behavior while extending evidence for nonce-based recovery.

7. **EXE-07: connect Jito reconciliation to accounting.** Persist the known bundle-to-execution mapping, derive quantities from attributable chain receipts, update `trades.signature`, and use existing evidence deduplication to advance positions and exposure. Do not label a landed signature a quantified fill without receipt amounts. Retain generic coordinator escalation on missing evidence (`apps/trade-executor/src/reconciliation-venues.ts:14-22`). Preserve legacy pending records when adding fields.

8. **EXE-08 and freshness: make readiness explicit.** Share RPC resolution between signer and simulator; prohibit live route readiness with a missing mandatory gate. Check source, quote, simulation and blockhash age immediately before signing/submission. PM has resolution-relative source staleness, while RHC computes a 120-second deadline before a possible approval receipt wait (`apps/trade-executor/src/polymarket.ts:797-843`; `apps/trade-executor/src/robinhood.ts:795-851`). Requote/resimulate after approval rather than silently extending an old price. Track final-artifact expiry; the simulator currently replaces the blockhash (`apps/trade-executor/src/solana-simulation.ts:225-240`).

## C. Invariants and isolated-test descriptions

No tests were run. Suggested local-only tests use in-memory ports, fixed clocks, harmless synthetic accounts and fake venue responses; they must not import entrypoints that start Redis/timers or load `.env`.

- Distinct user A/user B/operator claims and trade inserts retain their identities, including shared paper settlement; duplicate tenant/source/mode cannot reapply fills (EXE-02, `packages/db/src/copy-trade-lifecycle.ts:1834-1849`).
- Missing/expired/revoked grants and missing actual vault addresses deny before any signer call; paper/off mode never reaches a live transport (EXE-01/03).
- NaN/infinite/negative risk inputs cannot pass; parallel pending reservations cannot exceed a finite ceiling; paper and live cannot contaminate each other (EXE-04).
- Intent inspection rejects extra instructions or wrong owner/recipient/amount even when fake simulation succeeds (EXE-05).
- Simulate crashes before/after POST, lost responses and durable-store failure; unknown effects remain reserved and no second build/sign occurs without proof (EXE-06/09).
- Jito landed/failed/timeout resolutions update or escalate the right canonical execution once, using exact receipt quantities (EXE-07).
- Test raw quantities at `2^53-1`, `2^53`, and above without endpoints. Solana SELL rejects unsafe `Number` conversion, and Jupiter verifies safe input (`apps/trade-executor/src/solana-dispatch.ts:101-106`; `packages/shared/src/jupiter.ts:170-172`). This prevents silent raw-unit rounding but denies large legitimate sells; BigInt/string transport is the compatible enhancement. Human-unit receipt/reporting paths still convert to Number (`apps/trade-executor/src/index.ts:1987-1988`; `apps/trade-executor/src/robinhood.ts:929-930`); exact end-to-end financial precision is **NOT VERIFIED**.
- Breaker remains account/chain scoped; nonce contention is excluded from venue failures (`apps/trade-executor/src/index.ts:975-980,1020-1023`). Exercise lost lock-session behavior with fakes before proposing stronger nonce recovery; RHC advisory-session loss during an ongoing RPC was not tested (`packages/db/src/evm-nonce.ts:94-126`).

### Latency evidence, not performance promises

Source detection upstream of signal-engine was **NOT VERIFIED**. Signal-engine has immediate pub/sub-triggered processing plus authoritative 15,000-ms polling; polling phase and outages produce jitter, not a universal 15-second delay (`apps/signal-engine/src/index.ts:693-724`). Sequential fan-out and per-chain queue depth add unbounded waiting absent an admission deadline (`apps/signal-engine/src/fanout-enqueue.ts:349-359`). Quote timeout defaults to 8,000 ms; build is 8,000 ms; optional simulation is 5,000 ms; Jito request timeout is 10,000 ms (`packages/shared/src/jupiter.ts:23-25`; `packages/shared/src/jupiter-swap.ts:25`; `apps/trade-executor/src/solana-simulation.ts:376`; `apps/trade-executor/src/jupiter-jito-config.ts:114`). These deadlines are neither measured latency nor a summed end-to-end guarantee; tip reads and tip-blockhash RPC add separate serial dependencies (`apps/trade-executor/src/jupiter-jito-runtime.ts:282-311`; `apps/trade-executor/src/solana-signer.ts:80`). Jito pending TTL defaults to 600,000 ms and reconciliation polls every 60,000 ms (`apps/trade-executor/src/jupiter-jito-config.ts:28`; `apps/trade-executor/src/index.ts:2920`). PM settlement wait defaults to 30,000 ms, whereas reported `latencyMs` measures only `postOrder` (`apps/trade-executor/src/polymarket.ts:878-881,910-919`). RHC `latencyMs` starts after quote/approval/simulation (`apps/trade-executor/src/robinhood.ts:881-944`). Stored `submittedAt` begins before dispatch and PM preparation, not at actual network submission (`apps/trade-executor/src/index.ts:1761,2277`). Lifecycle helper preserves null/backwards stamps and contains no target (`apps/trade-executor/src/solana-latency.ts:39-59`). No percentile, speedup, universal-speed, sandwich-immunity or observed SLA claim is supported by this static review.
