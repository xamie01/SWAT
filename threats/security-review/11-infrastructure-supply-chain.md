### INF-01 — Production deploy executes an unpinned installer with deployment secrets

**High; high confidence; Verified source chain, Likely supply-chain compromise impact.** Both `/home/xahmie/Documents/SWAT/.woodpecker.yaml:68–90` and `/home/xahmie/Documents/SWAT/.woodpecker/ci.yaml:68–90` inject three Vercel secret references at lines 74–79, then execute `npm install -g vercel@latest` at line 83. The subsequent pull/build/deploy commands use the token and pull production environment material. These are separate from the frozen workspace install at line 25. All Node/service images use mutable tags, without content digests.

Abuse chain: compromised registry release → install/build execution → deployment credential or production environment access. This is not a claim that Vercel or an image is compromised. Exact lifecycle-script behavior of the fetched dependency graph is unverified, but installing third-party executable code in the secret-bearing step is explicit.

1. Commit an exact Vercel CLI version into the managed dependency graph and verify its lockfile integrity; remove `@latest` and global ad-hoc installation from both pipelines. Pin CI and database/cache image digests, with reviewed update automation.
2. Separate credential-free acquisition/build from a minimal deploy step. Give that step only the necessary project-scoped deployment credential, no broad production secrets; avoid pulling production environment into the shared checkout unnecessarily. Exclude `.vercel` and build caches from reusable artifacts.
3. Preserve Corepack/pnpm compatibility (`package.json:4` pins pnpm 10.2.0); coordinate both YAML copies or deliberately retire one. Vercel prebuilt output and web tracing must still work after step isolation.

### INF-02 — Documented production applications run as root; hardened alternative cannot use its code path

**High; high confidence; Verified conflicting artifacts, Likely host compromise amplification.** `/home/xahmie/Documents/SWAT/DEPLOYMENT.md:304–379` supplies four root-run service definitions for API, web, LP and executor, and line 385 enables them. Dependency/application code therefore inherits root when operators follow this runbook. Conversely, checked-in `deploy/systemd/swat-api.service:8–19`, `swat-trade-executor.service:8–23` and `swat-billing-sweep.service:7–15` use `User=swat` and `ProtectHome=true`, but put working directory, environment and executable beneath `/root/SWAT`. `ProtectHome=true` makes that home hierarchy inaccessible; ordinary `/root` traversal also obstructs the service user. The cron example likewise changes into `/root/SWAT` as `swat` (`deploy/crontab.example:4,13`).

Abuse chain: application/dependency execution → root privileges → host-wide persistence. The hardened units' predictable start failure encourages replacing them with the root runbook, but that operator response is not proven. Billing is not exclusively dependent on the broken timer: `apps/api/src/index.ts:328–340` schedules a built-in sweep unless disabled.

4. Consolidate the runbook and checked-in units around an unprivileged account, code under `/opt/swat` or `/srv/swat`, root-owned read-only releases and separately writable state/log directories. Keep `ProtectHome`, `NoNewPrivileges` and private temp isolation; add bounded filesystem writes and an empty capability set as compatible.
5. Move secret provisioning outside the repository to a restricted `/etc/swat` environment file or systemd credentials; audit API/executor/billing/LP/web consumers separately. Correct cron paths and choose one billing scheduler. Do not “fix” access by running as root or making `/root` public.

### INF-03 — Default application database identity is the bootstrap superuser

**Medium; Likely.** The default-bootstrap-role hazard is retained but downgraded from High because actual image role flags and runtime deployment are **NOT VERIFIED**. `/home/xahmie/Documents/SWAT/docker-compose.yml:13–18` sets the PostgreSQL bootstrap identity from `POSTGRES_USER`, defaulting to the same role used by application documentation (`DEPLOYMENT.md:184–187`); PgBouncer reuses it at `docker-compose.yml:45–50`. Official-image bootstrap-superuser semantics are assumed, not inspected from fetched image source. `packages/db/src/client.ts:10–27,65–67` constructs its application pool directly from `DATABASE_URL`, with no production role rejection. Migration `packages/db/sql/064_row_level_security.sql:47–64` creates a separate non-superuser, non-bypass application role, but the runbook does not switch runtime connections to it. Its bypass helper explicitly protects that named app role, while other identities can take the unset-context bypass (`:29–43`). CI setup is intentionally broader (`packages/db/src/ci-setup.ts:18–28` grants role/database creation capability), not evidence of production privilege.

Abuse chain: application SQL compromise → privileged database identity → tenant-control bypass/database administration. A weak committed default password is a bootstrap/template hazard, not a newly discovered live secret. Defaults bind database/cache/pooler host ports to loopback (`docker-compose.yml:20,33,44`), reducing direct Internet exposure.

6. Separate bootstrap/migrator, tenant application and explicit maintenance identities. Provision non-default passwords outside source; require a least-privilege production `DATABASE_URL`, reject superuser/BYPASSRLS startup identities, and restrict role memberships.
7. Preserve privileged worker/admin use cases through explicit narrow roles and transaction-scoped tenant handling rather than one global owner connection. Check API, executor, LP, billing sweep and migration callers before switching: global billing queries cannot simply inherit a tenant-only connection.
8. Keep migrations on a direct database connection. `packages/db/src/migrate.ts:16–36` takes a **session-level** advisory lock across separate transactions; routing that CLI through PgBouncer transaction pooling can break lock ownership/unlock semantics. Application pooling remains transaction-compatible only with appropriately scoped session state.

### INF-04 — Web rewrites default to plaintext cross-host backend transport

**High; high confidence; Verified default forwarding chain; actual remote overrides NOT VERIFIED.** `/home/xahmie/Documents/SWAT/apps/web/next.config.ts:4–17` accepts any string beginning with `http` and falls back to non-loopback HTTP targets. Rewrites forward `/v1/lp/*` and `/v1/*` there (`:24–35`). CI deploys the web app to Vercel (`.woodpecker.yaml:84–90`), so absent overrides this is not an encrypted loopback hop. A local reverse proxy alone does not protect direct backend ports or a remote HTTP rewrite.

Abuse chain: plaintext backend hop → session/request interception → authenticated request misuse. Header/cookie preservation at the actual hosting platform was not tested; transport loss is source-verifiable regardless.

9. Parse backend targets with `new URL`; fail production builds on unset/unapproved remote targets and require HTTPS for cross-host routes. Permit HTTP only for explicit local/private same-host development scenarios. Verify backend certificates and origin access controls outside this offline review.
10. Restrict backend bind addresses/firewall rules and make intended public gateways explicit. Preserve web cookie/proxy behavior and both API/LP rewrite ordering. Review MCP exposure separately; no Internet reachability is asserted here.
