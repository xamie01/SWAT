Most important results:

1. **The new Jito settlement wiring uses the wrong identity type.** Canonical client order IDs are `swat-` plus a digest; the new caller passes them to a `$2::uuid` signal filter. Redis is marked resolved before this failing database update. Even the legacy UUID path does not record receipt quantities, USD amounts, fees or canonical fill evidence.
2. **Close-all now passes the old pending-entry gate, but its trade insert lacks `exit_lot_id`.** That cannot satisfy migration 061 for a new source-less exit trade. Canonical paper evidence can already have committed before the compatibility trade write fails.
3. **Tenant propagation is materially improved, but fan-out still is not per-tenant executable.** The first confirmed execution makes the shared signal `executed`; later tenants without an existing execution are then rejected by the canonical claim function. Operator-first, default-concurrency-one processing makes this a normal ordering problem, not merely a race.
4. **Master sell sizing remains unsafe at two boundaries.** No lots for the selling master falls back to aggregate inventory, and existing master lots are not reduced by their outstanding reservations when sizing another sell.
5. **The operator Jupiter signer still signs economically uninspected final messages.** Nonempty valid transaction structure and successful simulation are not approval of the actual transfers, recipients, approvals, fees, or accounts.

Explicit `SOLANA_SIMULATION_ENABLED=false` is still an opt-out. Those are not claims of completed mandatory simulation across every venue.

### Details that change remediation conclusions

- **EXE-02's original write omission really was repaired at the reviewed call sites.** `recordTrade` injects the principal-derived user ID, the canonical claim receives it, and the database evidence writer derives ownership from the execution. The residual issue is not “userId still absent everywhere”; it is shared source terminal-state coupling, optional/unvalidated explicit execution loading, and remaining globally keyed controls.
- **SIG-02 is not fixed by only changing the multiplied quantity.** With A=10, B=90 and A's pending sell reservation=8, the new SQL can still size a distinct A sell to `min(92,10)=10` because it subtracts only aggregate reservations. No lot rows for A explicitly selects the aggregate fallback. SQL locks serialize the calculations but do not correct those calculations.
- **SIG-03's old pending gate is now exempted.** However, a real lot exit is required by `/home/xahmie/Documents/SWAT/packages/db/sql/061_copy_position_lot_exits.sql:19-29` to have `source_sell_fraction IS NULL`. The current Solana and Robinhood live branches require a truthy source fraction for every canonical sell (`/home/xahmie/Documents/SWAT/apps/trade-executor/src/index.ts:1760-1763,2108-2110`). This is a contract mismatch, presently masked for genuine user-live jobs by authority denial, not successful support for those exits.
- **SIG-04 has real but incomplete quantity fixes.** Solana receives a maximum raw token amount and Polygon receives explicit stop-loss shares. Trojan's preparation respects the maximum (`/home/xahmie/Documents/SWAT/apps/trade-executor/src/trojan.ts:150-171`). That does not supply canonical lot identity/reservations, repair Robinhood's default full-balance quantity, or justify guessing Solana decimals. Robinhood's final `submitAndWait` implementation was not re-read; the full-balance quote and encoded swap handoff were read, so external over-sale remains **Likely**, not an observed/fully re-executed effect.
- **EXE-05's amount comparison is useful but not transaction authorization.** ExactIn input and ExactOut output quantity equality are now checked. Missing mint fields can pass the quote check, but the build helper rejects missing mints, so missing fields alone are not asserted to cause a wrong-mint live swap. A fully populated malicious build still reaches the signer. Also, the operator adapter takes settlement identity from `TROJAN_WALLET_ADDRESS` and signing identity from the Jito signer without an equality check (`/home/xahmie/Documents/SWAT/apps/trade-executor/src/execution-authority-adapters.ts:219-242`); different configured accounts therefore need explicit route-account binding, not metadata-only trust.
- **EXE-06 is post-send bookkeeping, not write-ahead.** Both the success save and the newly added retryable-error save occur after `submitJitoBundle`. Clean persisted pending/terminal canonical states do prevent ordinary re-delivery; that containment does not prove an atomic submit claim, survival of a failed save, or recovery from an invented bundle ID.
- **EXE-07 is not fixed by updating only `status`.** Pending `persistTrade` writes leave actual monetary/token values null. The new settlement helper supplies no receipt amounts or fees and does not apply canonical evidence. A status-only update also makes the exposure sum overlook that unquantified fill.
