# API / web post-remediation security and logic review

## Scope and evidentiary limits

- Review date: 2026-11-08. HEAD confirmed as `8905505595802c21053118b5fab3fd53a8a1654c`; baseline `d5852a0e31e8e9a517c6e7c47ed9623819c7fc71`; remediation `ec3c5fefe4424be4d9a015a7402e2cfc7d8c6ab7`.
- Bounded partition: `apps/api`, selected `apps/web` consumers, `pda-test-ui`, LP authentication/CORS, and directly needed database helpers/schema. This is not a monorepo review or a deployment certification.
- **Verified means source trace, not a successful exploit, test, or observed deployment behavior.** Likely identifies a conditional security consequence with an observed source path. Needs check identifies an unexamined dependency, runtime, or deployment fact. Severity applies to the concrete prerequisite stated, not an assumed internet-wide compromise.
- No application changes, tests, builds, syntax-check executions, service starts, network requests, credential files, actual application logs, runtime captures, or real-account key derivation. Source-reading shell calls were sequential and CPU-pinned. The approved redacting reader was used for source/test material. Several early outputs were truncated; they are not counted as complete reviews. Exact successful ranges and exclusions are in the coverage artifact.
- The remediation report is a **specification to verify**, not evidence that its claims are true. The scoped working-tree diff check against HEAD returned no differences for the checked paths.

## Result

The blanket completion claim is not supported by this partition. The 23 prior IDs map to **5 closed(source), 13 partial, 4 open, and 1 surface-removed**. These are overlapping historical IDs, not 23 independent vulnerabilities. The PF findings below likewise include retained issues, regressions, and newly identified logic defects; they are not all newly introduced by the last commit.

**Coordinator follow-up:** `verification.md` records later isolated reproduction of invalid delegation acceptance, payment-attribution/event-type failures, plaintext SSR selection and the PDA syntax failure, plus selected existing passing regressions. The shared RPC/logging and LP error paths excluded by this source-only partition were subsequently read in `data-indexer-review.md`. No real credential or deployed endpoint was inspected; final combined dispositions are in `closure-ledger.json`.

The most consequential source-traced problems are:

1. The new Robinhood delegation handler inserts an authentication wallet before checking its signature, and signature recovery never gates success. That unproven wallet is subsequently trusted by billing and withdrawal-destination checks.
2. Billing still accepts an owned intent unrelated to the submitted on-chain payment. Separately, the Polygon verifier never verifies the ERC-20 event signature: a matching standard Approval event can satisfy its supposed transfer test.
3. Robinhood enrollment fabricates a different account address, does not establish on-chain delegated authority, and does not preserve the nonce/deadline needed to verify the signed policy later.
4. The PDA test server now has a duplicate lexical declaration that prevents parsing. Its remaining runtime-path findings below are therefore **dormant in this exact source until that error is repaired**, not claims of a currently running exploitable listener.

## Robinhood challenge → signer → persistence → consumers

- **Principal and sender:** `requireUser` selects the database tenant; body `address` is nevertheless independently trusted by the new wallet-link write. Wallet auth subsequently uses `user_auth_wallets` for wallet-only login (`/home/xahmie/Documents/SWAT/apps/api/src/auth/routes.ts:336-377`) and billing/withdrawal destinations. The legitimate wallet-login path does verify its SIWE signature; this review does not claim it accepts unsigned login.
- **Account/chain/domain:** the challenge hardcodes chain 4663 and a verifying contract, but generates a different address by string substitution. Hardcoded public chain IDs, addresses and verifying-contract identifiers are not confidential tokens. The client signs an API-supplied typed-data object without validating its expected fields; a compromised API response is therefore still a browser signing trust boundary, not proof of an already compromised API.
- **Nonce/expiry:** no stored user-bound challenge or one-use nonce; caller timestamp controls signed expiry, persisted expiry is unrelated server-now. Generic active-grant and vault readers do not inline-check expiry. A separate lapse-retirement helper exists; its scheduling and execution are excluded.
- **Policy/persistence:** sealed `{ address, smartAccount, signature, delegatedAt }` and metadata `{ smartAccount, dailyCap, chainId, delegatedAt }` are not the complete signed authorization. No on-chain target/selector/argument constraints, session key enrollment or receipt are established by this route. The envelope context includes the tenant and chain kind; this review did not open any envelope or inspect wrapper keys.
- **Consumer limit:** API vault rendering, authentication-wallet lookup, billing/withdrawal consumers, and database grant reads were traced. Trade-executor, bundler/paymaster and on-chain policy consumers were deliberately not reopened. Consequently an accepted database grant is not asserted to execute a trade or transfer funds.

## Sensitive-data and browser trust conclusions

- **Full CLOB tuple versus identifier:** the API constructs `{ apiKey, secret, passphrase, signerAddress }` for server-side sealing, while enrollment/vault responses expose the identifier only. No complete tuple, actual private key or confidential production token was observed. No real values were sought.
- **Proof versus root secret:** the removed explicit Polymarket proof log was an authorization-signature disclosure, not disclosure of a wallet private key. Remaining diagnostic exception serialization must not be assumed safe or assumed to contain the entire proof without a trace. Fastify/Pino logging is distinct from the shared console interceptor; this review does not assert that Pino messages enter Redis log streams.
- **URL versus secret:** a provider URL is sensitive only if it contains confidential components. Removing query/userinfo does not cover path tokens. Public network addresses, explorer links, chain IDs, project IDs and WalletConnect/Reown project identifiers are not private credentials merely because they are literals or `NEXT_PUBLIC_*` values. AppKit's project ID is intended to be browser-visible; relay origin/quota configuration was not inspected.
- **Own data versus unauthorized disclosure:** own-user API-key identifier display and admin-only diagnostics/export are not evidence of cross-tenant leakage. The inspected API client sends cookies/CSRF, not a shared privileged browser API key. No repository-wide or built-bundle secret scan is claimed.
- **SSR/browser boundary:** the SSR helper intentionally forwards only `swat_session` and uses no-store, but resolves an insecure fallback independently from middleware/config. AppKit creates a per-provider QueryClient with `useState`, a useful SSR cache-isolation choice; package internals and hydration behavior were not tested. No CSP header configuration was located in the inspected Next config/layout, but edge/application-wide header coverage is excluded, so this is not a universal absence claim.
